# Задание 5. Cutover-план миграции

## Результат

Разработан cutover-план перевода процессов записи пациентов, учёта пациентов и
учёта оплаты услуг с ручного ведения в Excel, сканах и 1С на новую платформу
сервисов из задания 2. Полный документ - [cutover_plan.md](cutover_plan.md):
обоснование выбора стратегии, поэтапный план в виде таблицы с пояснительным
текстом, план отката, реестр рисков и распределение ролей.

## Выбранная стратегия: Parallel run

Старый процесс - это преимущественно ручной труд и Excel, а не программный
монолит с техническими швами, поэтому Branch by abstraction неприменим
(абстрагировать нечего), а High-level design - это принцип проектирования целевой
системы, а не способ переключения нагрузки. Parallel run выбран потому, что:

- позволяет прогонять одни и те же записи и платежи через старую и новую систему
  и сверять результат до полного переключения - ключевой аргумент для
  медицинских и платёжных данных;
- нагрузку можно переводить порциями (по типам записей и филиалам), а старый
  процесс до последнего момента остаётся рабочим резервом;
- откат на ранних этапах сводится к возврату основной роли ручному процессу.

Ограничения подхода (двойной ввод, необходимость синхронизации двух хранилищ,
повышенный расход ресурсов) закрываются автопереносом записей, временным наймом,
ETL с ежедневной сверкой и ограничением окна параллельной работы 4-6 неделями.

## Этапы cutover-плана

0. Подготовка - инфраструктура, команда, критерии успеха, чек-лист 152-ФЗ.
1. Разработка сервисов MVP и первичная загрузка данных через ETL с тегированием
   категорий и проверкой качества.
2. Настройка синхронизации между старой и новой системами, определение источника
   истины по каждому домену, ежедневная сверка.
3. Параллельный запуск: обе системы работают, основной - старый процесс, идёт
   сравнение результатов, портал пациента открыт пилотной группе.
4. Постепенный перевод нагрузки canary-порциями 10 -> 50 -> 100 процентов с
   контролем метрик и автооткатом порции.
5. Полное переключение в окно выходного дня по решению Go/No-go, Excel переводится
   в режим только для чтения.
6. Стабилизация (hypercare) 2-4 недели: усиленный мониторинг, аудит доступа,
   разбор инцидентов.
7. Вывод старого решения из эксплуатации, архивация Excel и сканов в защищённое
   шифрованное хранилище.

## Управление рисками

Точка невозврата - завершение этапа 7. До неё откат возможен на каждом этапе: на
этапах 3-4 - переключением флага маршрутизации на старый процесс, на этапах 5-6 -
восстановлением Excel из read-only снапшота с обратной выгрузкой изменений из
новой системы. Определены стоп-критерии отката: потеря или порча данных пациентов
и платежей, недоступность записи дольше порога, расхождение платежей с 1С выше
допустимого.

Главный риск Parallel run - рассинхронизация данных между системами. Он
закрывается ежедневной задачей сверки, алертами на расхождения, единым источником
истины по каждому домену и блокирующим алертом по платежам с ежедневной сверкой с
бухгалтерией. Прочие ключевые риски: низкое качество исходных данных, утечка ПДн
при миграции, несоответствие 152-ФЗ, перегрузка ресепшена двойным вводом, скрытые
дефекты под нагрузкой, срыв сроков из-за найма, отказ единственного физического
сервера - для каждого в [cutover_plan.md](cutover_plan.md) описаны меры и действия.

## Роли

Спонсор проекта, Cutover-менеджер, Архитектор (технический директор), Владелец
продукта (бизнес-аналитик), команда разработки, инженер данных и DBA, QA-инженер,
DevOps и SRE (администратор сети и найм), специалист по ИБ и DPO, руководитель
ресепшена, представитель бухгалтерии, служба поддержки на период hypercare.
Ответственность каждой роли по этапам расписана в таблице cutover-плана.
