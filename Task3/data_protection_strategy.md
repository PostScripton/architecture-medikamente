# Стратегия защиты данных at rest и in transit

## 1. Классификация данных

Данные классифицированы по состоянию (при хранении / при передаче / при обработке), уровню чувствительности и профилю риска. Классификация основана на процессах, описанных в `project_overview.md`: запись пациента, ведение медицинской карты, учёт анализов, оплата услуг, кадровый и складской учёт.

### PII (персональные данные пациента)

Ф. И. О., дата рождения, телефон, email, адрес прописки, место работы или учёбы.

- Состояние: at rest (Excel/скан на общем диске, после миграции - Сервис записи и CRM), in transit (портал пациента, ресепшен, интеграция с лабораторией).
- Чувствительность: высокая.
- Профиль риска: прямая идентификация пациента, попадает под 152-ФЗ, при утечке - штрафы и репутационный ущерб.

### Специальная категория данных (медицинские данные)

Медицинские карты, диагнозы, результаты анализов, сведения о хронических заболеваниях.

- Состояние: at rest (Сервис медкарт и анализов, файловый сервер), in transit (интеграция с лабораторией, портал пациента, мобильное приложение).
- Чувствительность: критическая - специальная категория персональных данных по 152-ФЗ, требует повышенного уровня защиты.
- Профиль риска: наибольший репутационный и юридический риск компании, данные не подлежат восстановлению после утечки доверия пациента.

### Платёжные данные

Реквизиты платежа, история операций, данные ККМ и эквайринга.

- Состояние: at rest (1С:Бухгалтерия, Сервис платежей), in transit (ККМ, платёжный шлюз, эквайринг).
- Чувствительность: высокая, частично подпадает под требования PCI DSS (при обработке карточных данных).
- Профиль риска: финансовые потери, мошенничество, требования регуляторов к обработке платёжных данных.

### Кадровые и бухгалтерские данные (HR)

Паспортные данные сотрудников, зарплата, налоговые отчисления.

- Состояние: at rest (1С:Бухгалтерия предприятия), in transit (обмен с налоговыми органами, банком-эквайером зарплатных карт).
- Чувствительность: высокая, персональные данные сотрудников по 152-ФЗ.
- Профиль риска: юридическая ответственность работодателя, утечка ведёт к искам сотрудников.

### Аутентификационные данные

Пароли, токены сессий, ключи API, доменные учётные записи Active Directory.

- Состояние: at rest (Active Directory, IAM), in transit (все запросы через API Gateway и портал).
- Чувствительность: критическая - компрометация даёт доступ ко всем остальным категориям данных.
- Профиль риска: полная компрометация системы при утечке или переборе.

### Внутренние операционные данные

Учёт ТМЦ, закупки оборудования, складские остатки.

- Состояние: at rest (1С:Торговля и склад), in transit (обмен между 1С:Бухгалтерия и 1С:Торговля и склад).
- Чувствительность: низкая, данные не персонифицированы.
- Профиль риска: минимальный, ущерб ограничен внутренними бизнес-показателями.

### Данные аудита и мониторинга

Журналы доступа, логи действий пользователей, алерты о нетипичном поведении.

- Состояние: at rest (система мониторинга и алертинга), in transit (сбор логов от всех сервисов).
- Чувствительность: средняя - сами по себе не идентифицируют пациента напрямую, но раскрывают, кто и когда обращался к чувствительным данным.
- Профиль риска: при утечке или подделке логов теряется возможность расследовать инциденты.

## 2. Обоснование необходимости защиты и инструменты по классам данных

- **PII**
  - Необходимость защиты: прямое требование 152-ФЗ, риск идентификации пациента третьими лицами, утечка ведёт к репутационным и финансовым потерям.
  - Инструменты: TLS 1.3 для in transit, шифрование столбцов PII в базе данных (pgcrypto для Postgres), маскирование в интерфейсах ресепшена и CRM, RBAC/ABAC на уровне API Gateway.

- **Специальная категория данных (медицинские данные)**
  - Необходимость защиты: наивысший уровень чувствительности среди всех данных компании, юридические требования к обработке специальной категории персональных данных, репутационный риск при утечке диагнозов.
  - Инструменты: шифрование на уровне приложения (envelope encryption) до записи в хранилище, KMS для управления ключами, TLS 1.3 для интеграции с лабораторией и мобильным приложением, обезличивание перед передачей в аналитический слой, тегирование `SPECIAL_CATEGORY`.

- **Платёжные данные**
  - Необходимость защиты: требования к обработке платёжных данных, риск мошенничества, единый источник платёжных данных вместо ручного дублирования в Excel и 1С.
  - Инструменты: токенизация номеров карт на стороне эквайринга, шифрование канала ККМ - Сервис платежей - 1С:Бухгалтерия, шифрование базы данных Сервиса платежей, разграничение доступа для бухгалтерии и кассиров.

- **Кадровые и бухгалтерские данные**
  - Необходимость защиты: персональные данные сотрудников по 152-ФЗ, юридическая ответственность работодателя.
  - Инструменты: шифрование файловой базы 1С:Бухгалтерия предприятия на уровне диска (BitLocker/LUKS), ограничение доступа по ролям (только бухгалтерия и технический директор), шифрование резервных копий.

- **Аутентификационные данные**
  - Необходимость защиты: компрометация даёт доступ ко всем остальным категориям данных, единая точка отказа при отсутствии защиты.
  - Инструменты: хранение только хешей паролей (bcrypt/argon2), многофакторная аутентификация для доступа к чувствительным доменам, TLS для всех запросов аутентификации, ротация ключей API через KMS.

- **Внутренние операционные данные**
  - Необходимость защиты: базовая защита от несанкционированного изменения складских остатков, коммерческая тайна закупочных цен.
  - Инструменты: шифрование канала обмена между 1С:Бухгалтерия и 1С:Торговля и склад, ролевой доступ на уровне 1С.

- **Данные аудита и мониторинга**
  - Необходимость защиты: целостность логов нужна для расследования инцидентов и подтверждения соответствия 152-ФЗ.
  - Инструменты: запись логов в отдельное защищённое хранилище с ограничением на изменение (append-only), шифрование канала передачи логов в систему мониторинга, контроль целостности через хеширование записей.

## 3. Автоматизированный контроль

- **CI Data-Guard.** Проверка релизов перед выкладкой на корректную работу с тегированными данными (`PII`, `SPECIAL_CATEGORY`, `PAYMENT`, `HR`) - блокирует деплой, если новый код передаёт тегированные поля в нешифрованном виде или логирует их в открытом виде.
- **DLP-система.** Отслеживает попытки выгрузки чувствительных данных за пределы контролируемого периметра (например, копирование медицинских карт на внешний носитель или отправку по почте).
- **SIEM и аудит доступа.** Централизованный сбор логов доступа к данным, обнаружение нетипичных действий пользователей (массовая выгрузка карт пациентов, доступ в нерабочее время), автоматическая отправка алертов в систему мониторинга.
- **Автоматическая ротация ключей шифрования.** KMS ротирует ключи шифрования данных PII, SPECIAL_CATEGORY и PAYMENT по расписанию и при подозрении на компрометацию.
- **Контроль истечения TLS-сертификатов.** Автоматическая проверка и продление сертификатов на API Gateway и внешних интеграциях (лаборатория, эквайринг), чтобы исключить работу по незащищённому каналу.
